Reed — Design Principles & Terminology Proposal

Reed: Design Principles & Terminology Proposal

Reed · September 2026

Abstract

Reed is an incremental state synchronization engine for declarative dataflow applications. This document restates Reed's design principles and motivation in a form suitable for external review, and proposes a refinement of the three architectural terms — Depot, Outpost and Parcel — that internal working notes leave unsettled. The proposal aligns those terms with the loom metaphor Reed is itself named for, replacing Depot with Warp and Outpost with Heddle, while retaining Parcel after considering and rejecting alternatives that collide with existing concurrency terminology.

1. Motivation

Declarative dataflow applications express computation as a graph of typed transformations over state. As such applications grow, the dependencies between individual computations accumulate: a change to one piece of state may require several others to be recomputed, in a specific order, without leaving the system momentarily inconsistent. In the absence of a supporting runtime, developers track these dependencies and re-synchronize affected state by hand — orchestration code that is easy to get subtly wrong and that grows linearly with the number of dependent computations.

This problem is common to systems that must keep many strongly typed pieces of state consistent as they are produced, consumed and mutated across independent components. Reed factors that need into a standalone engine: developers declare computations as transformations over typed state, and the runtime is responsible for inferring dependencies between them and propagating updates incrementally, keeping application state consistent with minimal user-defined orchestration.

2. Origin of the Name

Reed takes its name from the reed of a weaving loom: a comb-like structure that aligns, separates and beats the warp threads into place as fabric is woven. The reed does not weave the fabric itself — it keeps many parallel threads synchronized and correctly ordered as the loom's other mechanisms act on them.

“Reed organizes strongly typed pieces of application state, automatically coordinating their dependencies and keeping the states synchronized.”— the Reed README

The metaphor is a useful constraint on the engine's own vocabulary: a name drawn from weaving invites terminology drawn from the same craft, rather than from an unrelated domain. Section 4 argues that the project's current vocabulary only partially honors this constraint, and proposes a correction for the terms still under discussion.

3. Design Principles

Reed's architecture rests on six principles, each stated here as a testable commitment rather than a label:

PrincipleCommitment
State-orientedComputation revolves around synchronized state rather than direct communication between computations.
DeclarativeDependencies between computations are described, not manually orchestrated.
IncrementalOnly the computations affected by a given state change are recomputed.
Event-drivenState evolution is triggered by events, not by on-demand queries.
Strongly typedEvery artifact and every dependency between artifacts is statically defined.
LayeredTransport, synchronization, incremental computation and dataflow composition remain independent, separately replaceable concerns.

These principles are load-bearing rather than aspirational: they are also what distinguishes Reed's computational model from adjacent systems such as ROS 2 (event-driven but without a single shared state), Salsa (state-centric but query-driven and lazy rather than event-driven and eager), and Dagster (explicit dependencies over an asset graph, but oriented toward scheduled data pipelines rather than reactive, always-consistent application state).

4. Proposed Terminology

Reed's internal working notes single out three architectural terms — Depot, Outpost and Parcel — as still under evaluation, while treating the remainder of the vocabulary (Node, Bus, Port, Message, Flow, Transport, Synchronization, Activation, Composition) as stable. Depot and Outpost were both borrowed from logistics vocabulary: a depot as a centralized store, an outpost as a remote point of access to it. That vocabulary is coherent on its own terms, but it does not come from the same source as the engine's own name.

Reading the three unsettled terms against the loom metaphor instead yields the following:

Current termProposed termRationale
DepotWarpThe set of threads held under tension on a loom — the direct analogue of the authoritative, centrally held state that Reed synchronizes across every node.
OutpostHeddleThe cords that guide and lift individual warp threads so the loom can act on them selectively — the direct analogue of a node's synchronized, per-dependency interface into the Warp.
ParcelParcel (unchanged)Thread and Strand were both considered as the metaphor-consistent choice, and both rejected: Thread collides with the unrelated concept of an operating-system or execution thread, which this project must stay orthogonal to, and Strand reads as a synonym rather than a distinct concept. Parcel is retained as the clearer term.

Under this proposal, a node no longer "interacts with the Depot through an Outpost" — it interacts with the Warp through a Heddle, and the sentence reads as an extension of the same metaphor that names the engine, rather than a switch into a second one. No other term changes: Node, Bus, Port, Message and Flow already read consistently and are left as they are.

5. Conclusion

Reed's motivation is narrow and concrete: remove hand-written orchestration from declarative dataflow applications by making state synchronization, dependency inference and incremental recomputation the runtime's responsibility rather than the developer's. Its six design principles state that commitment precisely enough to be checked against the implementation. The terminology proposed here does not change what the engine does — it resolves an open naming question flagged in the project's own notes, in favor of the metaphor the engine is already named for, ahead of the public API and documentation work already planned.
